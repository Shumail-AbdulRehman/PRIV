## 1. WHAT THIS PROJECT IS

CleanOps is a multi-tenant cleaning / facility-operations management SaaS
(FYP). Business flow:

- A company signs up -> gets ONE ADMIN account (the company owner, web
  dashboard only).
- Admin creates locations (lat/long, geofence radius, IANA timezone
  auto-detected from coordinates) and managers. Each manager must be assigned
  >= 1 location; a location can belong to ONLY ONE manager (exclusive
  assignment, DB-enforced).
- Admin/managers create staff (mobile users with shift windows) and task
  templates (DAILY or ONCE recurrence, each with a unique QR token).
- Backend crons generate daily task instances from templates, auto-assign
  them to the best eligible staff, auto-reassign tasks not started within a
  grace period, and mark missed work.
- Staff use the Expo mobile app: login -> geofenced selfie check-in/out ->
  view today's tasks -> scan the location QR to start a task -> upload proof
  photos to complete it.
- Attendance and task outcomes roll up into manager dashboards (Today Status,
  location stats, staff detail).

## 3. CORE ARCHITECTURE

### Roles & tenancy

- Prisma `Role` enum: ADMIN | MANAGER | STAFF.
- ADMIN and MANAGER logins both live in the `Manager` table; staff login
  lives in the `Staff` table. Company is the tenant root.
- `verifyJwt` (backend/src/middlewares/auth.middleware.ts) accepts the
  `accessToken` cookie or `Authorization: Bearer`; loads the user, rejects
  inactive MANAGER/ADMIN accounts, and attaches `req.user.locationIds` for
  MANAGER (from `ManagerLocation`).
- `authorize(...roles)` middleware factory guards routes.
- `backend/src/utils/scope.ts`: `getScopedLocationIds` (null = ADMIN
  unrestricted) and `assertLocationAccess` (403 for out-of-scope MANAGER).
  All location/staff/task/attendance controllers enforce this.

### Auth tokens

- JWT access (default 15m) + refresh (default 7d). Refresh flow
  (`POST /api/common/refresh-token`) rotates both tokens, stores the refresh
  token server-side, and has REUSE DETECTION (mismatched stored token ->
  null it out + 403).
- Cookies configurable via `COOKIE_SECURE` / `COOKIE_SAME_SITE`; path `/`.
- Logout works without a valid access token (clears cookies best-effort).
- Passwords hashed by a Prisma client extension (bcrypt, 10 rounds) in
  `backend/src/prisma/prisma.ts` — invisible at call sites, keep in mind.

### Timezone model (IMPORTANT)

- `Location.timezone` = IANA name, default "Asia/Karachi" for existing rows.
- Every DB DateTime is a true UTC instant; wall-clock meaning comes from the
  owning location's timezone (09:00 at a Karachi location = 04:00Z).
- Day anchors (`TaskInstance.date`, `Attendance.date`) = start of the
  location's LOCAL day as a UTC instant (Karachi: 19:00Z previous UTC day).
- `backend/src/utils/dateTime.ts` holds the zoned helpers
  (`getZonedDayRange`, `getZonedDayRangeFromDateInput`, `getZonedMonthRange`,
  `getZonedClockMinutes`, `withZonedClockOnLocalDay`,
  `resolveZonedAttendanceWindow`, `isValidTimeZone`) plus legacy plain-UTC
  helpers. Location-scoped logic MUST use the zoned helpers (DST-safe).
- Timezone auto-detection: createLocation/editLocation derive tz from
  lat/long via tz-lookup when not explicitly provided (fallback "UTC").
- Web frontend formats per-record location tz via formatInTimeZone; time
  inputs convert via fromZonedTime; calendar-date-only values stay UTC.
- Mobile app: all date logic is still HARDCODED to Asia/Karachi
  (utils/attendance.ts, utils/format.ts) — known gap.

### Task lifecycle

- `TaskTemplate` (recurringType DAILY|ONCE, effectiveDate,
  recurringEndDate?, unique qrToken) ->
  crons create `TaskInstance` rows (`@@unique([templateId,date])` makes
  generation idempotent) ->
  `services/taskAssignment.service.ts` assigns: prefers template-designated
  staff, else `findBestStaffForTask` scores candidates by shift coverage
  (overnight-normalized), attendance eligibility, and current workload;
  race-safe transactions; everything written to `AuditLog`.
- Staff starts a task via QR token (`POST /api/task-instance/:id/start?qrToken=`)
  and completes with >= 1 proof image (max 5, Cloudinary).
- Statuses: PENDING / IN_PROGRESS / COMPLETED / NOT_COMPLETED_INTIME /
  MISSED / CANCELLED. Assignment statuses tracked separately in
  `TaskAssignment` with `isCurrent` history.
- Reassignment cron (every minute) reassigns ASSIGNED tasks past
  `TASK_START_GRACE_MINUTES` (default 10), max `MAX_TASK_REASSIGNMENTS`
  (default 3).

### Attendance

- Crons create daily ABSENT rows per staff (`@@unique([staffId,date])`).
- Check-in: haversine geofence vs `location.radiusMeters` (server-side),
  30-min early window, 15-min late grace, selfie to Cloudinary, atomic
  `updateMany` guarded on status ABSENT.
- Check-out: geofence, 30-min minimum shift duration, late checkout keeps
  MISSED_CHECKOUT status. Statuses: ABSENT / CHECKED_IN / CHECKED_OUT /
  LATE / MISSED_CHECKOUT.

### Cron jobs (backend/src/cron/, imported for side effects in app.ts)

- `dailyTaskScheduler` — runs at import AND every 90s via setInterval
  (KNOWN ISSUE: wasteful; should be per-location-midnight scheduling).
- `onceTaskScheduler` — node-cron `3-59/15 * * * *`.
- `taskStatusCron` — `7-59/15 * * * *`; expired PENDING -> MISSED,
  expired IN_PROGRESS -> NOT_COMPLETED_INTIME.
- `taskReassignmentCron` — every minute.
- `attendanceCron` — `2 */6 * * *` (every 6h); creates ABSENT rows +
  syncs open attendance windows (sequential loop — Promise.all was removed
  after Prisma pool P1017 connection deaths).
- `attendanceStatusCron` — `5-59/10 * * * *`; past expectedEnd ->
  MISSED_CHECKOUT.
- `startupCron` — catch-up superset, awaited on boot.

## 4. DATA MODEL (Prisma, backend/prisma/schema.prisma, 22 migrations)

- `Company` — tenant root.
- `Manager` — unique email, role (ADMIN/MANAGER/STAFF), refreshToken,
  company FK, assignedLocations via ManagerLocation.
- `Staff` — unique email, phone?, shiftStart/shiftEnd (wall-clock only),
  nullable locationId (SetNull), refreshToken; indexes on
  companyId/locationId/isActive.
- `Location` — latitude/longitude stored as STRING, radiusMeters (default
  500), timezone (IANA).
- `TaskTemplate` — title/desc, optional staffId, location FK, shift window,
  recurrence, unique qrToken. Legacy `referenceImageUrl` kept for backwards
  compatibility; new templates use `referenceImages TaskTemplateReferenceImage[]`.
- `TaskInstance` — denormalized template copy, date = local-day anchor,
  status, isLate/lateMinutes, startedAt/completedAt, proofImageUrls[];
  `@@unique([templateId,date])` + composite indexes. Legacy `referenceImageUrl`
  kept; new instances use `referenceImages TaskInstanceReferenceImage[]`.
- `TaskTemplateReferenceImage` / `TaskInstanceReferenceImage` — name, imageUrl,
  sortOrder, cascade delete with parent.
- `TaskAssignment` — per-instance assignment history (status, reason,
  isCurrent, lifecycle timestamps, Cascade delete).
- `Attendance` — unique [staffId,date], expectedStart/End, check-in/out
  times + selfie URLs, late fields.
- `AuditLog` — companyId?, actorType/actorId, entityType/entityId, action,
  reason, old/new Json.
- `ManagerLocation` — composite PK [managerId,locationId],
  `locationId @unique` (one manager per location).

Migration history tells the evolution: init -> indexes -> missed checkout ->
QR -> proof images -> radius -> query-optimization indexes -> assignments +
audit logs -> staff phone -> billing tables REMOVED -> location timezone ->
unique manager-location -> admin role + manager locations -> reference-image
verification -> multi-area reference-image verification.

## 5. API SURFACE (all under /api)

- `manager`: POST /manager-signup, POST /manager-login (public);
  GET /profile/me; GET /today-status (ADMIN,MANAGER);
  POST /, GET /, PATCH /:id (ADMIN only — create/list/update managers,
  409 on location-assignment conflict).
- `staff`: POST /staff-login (public); CRUD + /inactive + /details/:id +
  /location/:locationId (ADMIN,MANAGER, scoped); GET /profile/me.
- `location`: create/edit/deactivate/inactive/restore (ADMIN only);
  GET /, GET /:id, GET /:id/stats (ADMIN,MANAGER).
- `task-template`: CRUD + GET /location/:locationId (ADMIN,MANAGER).
- `task-instance`: GET /staff/:staffId/today, POST /:taskId/start?qrToken=,
  POST /:taskId/complete (multer, max 5 images), GET /:taskId,
  GET /location/:locationId.
- `assignment`: PATCH /staff/:staffId/location/:locationId,
  PATCH /task-template/:templateId/staff/:staffId.
- `attendance`: PATCH /staff/:id/shift, POST /check-in, POST /check-out
  (multer selfie), GET /my, GET / (ADMIN,MANAGER).
- `common`: POST /logout, POST /refresh-token (unauthenticated by design),
  GET /get-current-user.

Response envelope: ApiResponse `{statusCode,data,message,success}` /
ApiError `{success:false,message,errors}`. Zod v4 schemas in
backend/src/validations/.

## 10. KNOWN ISSUES / TECH DEBT (from deep analysis)

Security:
- No rate limiting anywhere (login endpoints brute-forceable).
- verifyJwt checks isActive for managers but NOT staff — deactivated staff
  access tokens stay valid until expiry.
- Mobile tokens in AsyncStorage, not SecureStore; cleartext HTTP allowed.
- Staff login returns tokens in the JSON body (XSS-exfiltratable on web).
- Both clients match refresh on the literal string "Access Token Expired".
- COOKIE_SECURE=false default in backend Dockerfile; login cookies omit
  sameSite (refresh/logout include it).
- Debug logging middleware left on POST /api/attendance/check-in; stray
  console.logs of staff/attendance data.

Correctness:
- Time-basis split: assignment.controller, attendance.controller
  (assignShiftToStaff), and Zod shift schemas use UTC clock minutes while
  taskTemplate/staff-edit/assignment-service use location-tz minutes — same
  validation can pass in one endpoint and fail in another.
- Grace-period drift: 5 min hardcoded in startTask/getTodayStatus vs
  env-configurable 10 min in the reassignment cron.
- getTodaysTasksForStaff lacks manager location scoping (any manager can
  read any same-company staff's tasks).
- signupManager creates company + admin non-transactionally (orphan
  company possible).
- editLocationSchema doesn't actually make fields optional — PATCH needs a
  full payload.
- ensureAssignmentsForToday scans ALL open instances, not just today's.
- Mobile date logic hardcoded to Asia/Karachi (contradicts per-location tz).
- Frontend: no 404; createLocation posts a `{data}`-wrapped payload;
  query-key fragmentation (["getLocations"] vs ["location"] vs
  ["dashboard-locations"]) leaves some lists stale after mutations.
- getMyAttendance checks role === "MANAGER" but not "ADMIN".

Housekeeping:
- Daily task scheduler polls every 90s (should be per-location scheduling).
- No tests anywhere (verification = tsc + manual smoke).
- Dead code: frontend common/ form components, several unused exports,
  App.css; mobile canCheckInNow/formatShortDateTime; backend unused vars.
- Data cleanup pending: test manager "tetsing" (id 9) has ZERO locations —
  reassign or delete.
- Manager-created staff with "No location" immediately disappear from that
  manager's Staff tab (location-less staff are admin-visible only).
- No EAS config; EXPO_NO_DEPENDENCY_VALIDATION=1 masks dep warnings.
- No root README; mobile README has stale paths (/home/shumail/FYP/...).

## 12. FEATURE (2026-08-18): AI Reference-Image Verification (single reference)

- Legacy single-reference tasks use `TaskTemplate.referenceImageUrl` and
  `TaskInstance.referenceImageUrl`.
- On task completion, the first staff proof image is compared with the single
  reference image. Both `location_match` and `cleanliness_match` must be >= the
  env thresholds (default 70). Legacy tasks without a reference image skip
  verification and complete as before (audit-logged).
- Provider-abstracted in `backend/src/services/verification/` (OpenAI / Gemini).
- Attempts stored in `TaskCompletionAttempt` with scores/reasoning/raw response.

## 13. NEW FEATURE (2026-08-18): Multi-Area Reference-Image Verification

- Task templates now support multiple named reference areas
  (`TaskTemplateReferenceImage`), e.g. "Sink", "Toilet 1", "Mirror". Each
  area has a name, image URL, and sort order.
- Daily/once crons snapshot template reference images onto each generated
  `TaskInstance` via `TaskInstanceReferenceImage` (idempotent, guarded against
  re-runs).
- Staff-facing endpoints expose only area names/sortOrder; managers see full
  image URLs.
- On completion, the staff must upload one photo per reference area, in the
  same order as the areas. The backend verifies each area independently:
  location match then cleanliness match, both against the env thresholds.
  If any area fails, the entire submission is rejected and per-area attempt
  rows are recorded under a shared `submissionId`.
- Legacy single-reference tasks continue to use the old verification path.
- Mobile CompleteTaskScreen uses camera-only capture (`launchCameraAsync`) for
  multi-area tasks to prevent gallery cheating; legacy no-area tasks keep the
  gallery picker.
- New env var: `MAX_REFERENCE_IMAGES` (default 10).
