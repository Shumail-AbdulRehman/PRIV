# Provider/hosting research — read 2026-11-06

Research angles: provider-owned card entry, environment/default-link initialization, server-owned transactions, signed activation events, browser build configuration and backend runtime configuration. Primary documentation only.

1. [Paddle overlay checkout](https://developer.paddle.com/build/checkout/build-overlay-checkout/) — use Paddle.js with sandbox client token and matching environment. Provider controls the card form and supports brand settings. Default payment link and valid matching price IDs are prerequisites. Sandbox supports its documented test card; no card input should be built into Hygene Ops itself.
2. [Pass a transaction](https://developer.paddle.com/build/transactions/pass-transaction-checkout/) — reuse a server-created transaction ID in checkout, preserving canonical ownership and duplicate-purchase protection.
3. [Default payment link](https://developer.paddle.com/build/transactions/default-payment-link/) — configure a destination page; payment links include a transaction query parameter. Preserve existing /choose-plan compatibility and handle SDK initialization once; sandbox/live settings are separate.
4. [subscription.created](https://developer.paddle.com/webhooks/subscriptions/subscription-created/) — subscription creation follows the relevant transaction lifecycle and may be followed by trialing/activated. A browser success URL does not itself prove persisted entitlement.
5. [Webhook signatures](https://developer.paddle.com/webhooks/about/signature-verification/) — authenticate exact raw bytes using the correct destination secret. Preserve the existing raw-body route and deduplication.
6. [Go-live checklist](https://developer.paddle.com/build/go-live-checklist/) — sandbox catalog, credentials, settings and notifications are separate from live. This plan targets sandbox only; no switch to live is implied by a successful test checkout.
7. [Netlify build environment](https://docs.netlify.com/build/configure-builds/environment-variables/) and [Vite environment](https://vite.dev/guide/env-and-mode) — VITE_ settings become public build-time configuration. Updating them requires a new frontend build; private server keys must not use that prefix.
8. [Heroku config vars](https://devcenter.heroku.com/articles/config-vars) — backend environment is runtime configuration, separately managed from the Netlify build. Diagnose configured names/environment/catalog/webhook destination without exposing keys.

Design decision proposed: retain Paddle overlay for this repair; it already exists and provides real hosted card fields. Build a coherent plan/summary/activation experience around it. Inline checkout remains possible but adds integration surface without resolving a disabled environment. No third-party checkout layout, unverified price amount or invented discount is product truth.

## Signup session continuity — additional deployment angle

Read 2026-11-06: [MDN credentialed CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) confirms browser third-party-cookie policy still applies even when credentials/CORS settings are correct. [Netlify rewrites/proxies](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/) documents external API proxy rewrites. Current deployed public browser requests go directly from Netlify to the Heroku origin; frontend/public/_redirects has an asset 404 and SPA fallback, but no API proxy.

Planning inference, not a proven live failure: signup could lose its HTTP-only session under restrictive cross-site-cookie settings. The diagnostic unit must verify actual Set-Cookie persistence and authenticated current-user on the real deployment, including a browser with third-party cookies blocked. If continuity fails, prefer a tested same-origin /api proxy before the SPA fallback, retaining the existing backend/webhook identity boundary and no-store behavior. Do not work around it by exposing refresh tokens to browser storage or asking customers to weaken privacy settings. Scope any proxy change to web; do not rewrite native API URLs. Verify supported provider proxy headers/cookie forwarding on the deployed preview before adopting it.
