# Spec 70 inventory: block reused task photos before the check

- `reusedPhoto({ companyId, locationId, areaId, publicId }, { sha256, normalizedHash, perceptualHash, hashVariants })` (`backend/src/services/verification-v2/directPhoto.service.ts`) returns `true` when the photo is a reuse. That means an exact `sha256` or `normalizedHash` match with a kept asset (`privacyState` not `DISCARDED`) anywhere in the company, or any hash variant within `REUSED_PHOTO_NEAR_DISTANCE` (2) bits of a kept asset of the same area at the same location in the last `REUSED_PHOTO_AREA_WINDOW_MS` (48 h), newest `REUSED_PHOTO_AREA_LIMIT` (200). It runs two queries in parallel on existing indexes.
- `processDirectPhoto` runs it as stage `reuse` after the quality check and before the AI and storage. A reuse is published as `RECAPTURE_REQUIRED` / `DUPLICATE_EVIDENCE` with `keep:false`: no AI, no upload, and an evidence row marked `DISCARDED`. When the check throws, the event `DIRECT_PHOTO_REUSE_CHECK_SKIPPED` is logged and the photo is checked as before. The claim read now includes `session.task.locationId`.
- `duplicateClassification(current, candidates, nearDistance = 8)` (`duplicate.service.ts`) takes an optional near distance. The old pipeline keeps 8.
- Staff text comes from the existing `staffPhotoInstructions` `DUPLICATE_EVIDENCE` case. Its eight forms have Urdu in `frontend-mobile/src/i18n/staffAppTranslations.ts`.
- Test: `backend/src/services/verification-v2/reusedPhoto.test.ts`. It uses an in-memory evidence table that applies the same filters as the queries, and it measures real hash distances on `docs/verification/evidence/photo-flow/*.jpg`.
